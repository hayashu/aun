# PRD量産 作成計画(ドラフト)

ペルソナA × ペルソナB のペインポイントを掛け合わせ、PRDとモックアプリを量産するための計画。
前提となるペインポイントは [README.md](./README.md) を正とする。

## 1. ゴール

- ペルソナAのペイン5つ × ペルソナBのペイン5つ = **25セル**
- 1セルにつきPRDを**3本** → **合計75本**
- PRD 1本につき、モックアプリ(単一HTMLファイル)を**1つ** → **合計75個**
- 各PRDは「問題定義 → 解決策」の流れで書く

## 2. 掛け合わせの軸

### ペルソナA(5つ)
| ID | ペイン |
|---|---|
| A1 | 相手の真意がわからない |
| A2 | 暗黙の期待・ルールがわからない |
| A3 | 適切なコミュニケーション方法がわからない |
| A4 | 失敗の原因がわからない |
| A5 | 安心して練習・相談できる場所がない |

### ペルソナB(5つ)
| ID | ペイン |
|---|---|
| B1 | やりたいものづくりができない |
| B2 | ハードウェアの知識が足りず焦る |
| B3 | 自分で進める道筋を作れない |
| B4 | 専門領域の違いで認識がずれる |
| B5 | 気軽に試して失敗できる場所がない |

セルIDは `A{n}xB{m}`(例: `A3xB4`)。PRDは `A3xB4-1`, `A3xB4-2`, `A3xB4-3` の3本。

## 3. 問題定義の作り方

1セルの問題定義は、AのペインとBのペインを**同時に抱える状況**として1つに束ねる。
- 書き方の型: 「Aのペインを持つ人が、Bのペインを持つ人と関わる/同じ場面にいるとき、〇〇が起きる」
- 2人が同じ組織・チームで出会う前提を、全PRDの共通の舞台にする(要確認: 4章)
- 無理にこじつけたセルは、PRD冒頭に「接点が弱い」と明記して残す(捨てない)

## 4. 同一セル内の3本の差別化

同じ問題定義に対して、解決策の**方向性を意図的に分ける**。3本が似たものにならないための軸:

| 版 | 方向性 | 例 |
|---|---|---|
| -1 | 当事者の行動を支える(個人向けツール) | 振り返り支援、練習アプリ |
| -2 | 2人の間をつなぐ(コミュニケーション設計) | 共通語彙の可視化、確認の型 |
| -3 | 場・仕組みを変える(チーム/組織向け) | ルール、ワークショップ、ボード |

要確認: この3分類でよいか。別の軸(技術で分ける、ユーザー体験で分けるなど)が良ければ差し替える。

## 5. PRDの構成(共通テンプレート)

形式は「あうん」本体PRD(Alpha+ PRD 101、Slide 27 テンプレート順)に揃える。見出しの順序と書き方は次のとおり。

### 見出しの順序

```
# PRD: <タイトル>（セルID・版）
版: v1（作成日） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ 一言の位置づけ(どのセルの何版か、同セルの他の版との違い)

---
## Overview / Problem Statement
## Goals / Non-Goals
## Proposed Solution / Feature Description
## User Stories
## Open Questions
## Risks（教材外補強 — PRD 101 に Risks の形式は無い）
```

### 各節の書き方
| 節 | 書き方 |
|---|---|
| Overview / Problem Statement | 具体的な人物(「製造業A社の〇〇さん、30代、〜」)と具体的な場面から入る。**誤解・損失の実態**を時系列で書き、**気づきの実態**、**練習機会の実態**、既存手段の空白、背景データの順に進める。ここでAとBの両方のペインを1つの場面に束ねる。段落の頭は太字ラベル(`**誤解の実態**:`)にする |
| Goals | 「〜が減る / 増える」の形で、各項目に**効果指標を括弧で付ける**(例: 「（〇〇の件数を効果指標とする）」)。制御できる目標とできない目標を分けて注記する |
| Non-Goals | 「やらないこと(理由)」の形。理由を括弧で必ず添える。隣接領域(既存サービス、評価・採点、代行など)を明示的に外す |
| Proposed Solution | 冒頭に解決策の核を2〜3文で述べる。続けて**主要な構成要素**を `**名前** — 説明` の箇条書きにする(目安5〜7個)。第2段階に回すものは「現時点のプロトタイプには入っておらず、第2段階に置く」と明記する |
| User Stories | `**US-001 〜問題**` に続けて「利用者は、〜したい。それにより〜したい。」と書き、`背景:` に現状と、その損失がいつ確定するかを書く。**1PRDあたり2〜3本** |
| Open Questions | 判断が割れる論点、測れていないもの、設計上のトレードオフを書く。1つにつき1〜3文。「何が掛かっているか」まで書く |
| Risks | `**名前** — 原因 → 経過 → 結果。軽減: 〜`(矢印で因果を示す)。5〜6個 |

### 本計画での調整点
- 量産のため、索引の節(「この PRD の構成」)は各PRDに置かず、`matrix.md` に集約する
- 同一セルの3本は、冒頭の「※」に**版の方向性**(4章)を1行で書く
- ペルソナ名は README.md の「ペルソナA / ペルソナB」で統一する。参考PRDの「Bさん」(外国籍社員)は本計画のペルソナBとは別人なので、人物名は流用しない
- 目安は1本あたり80〜120行
- **「モックで確かめたいこと」は専用節にせず、Open Questions の中に1〜2個書く**。モック作成時、サブエージェントはその項目を作り込みの指示として読む

## 6. モックアプリの仕様

- **HTMLファイル1つ**で完結(CSS/JSはインライン、外部通信なし。ライブラリが必要なら固定バージョンのCDN)
- PRDの「構成要素」のうち**主要1〜2つ**の操作が触れること。全機能は作らない
- ダミーデータをファイル内に埋め込む
- スマホ幅でも崩れないこと
- 1ファイル目安300行以内

## 7. 実行方式(オーケストレーション)

```
メインエージェント
  └─ for セル in 25セル
       └─ for 版 in 1..3
            1. PRDを書く                → PRD/<セルID>-<版>.md
            2. サブエージェントを起動     → PRDを渡し、モックHTMLを作らせる
            3. サブエージェントが完了     → HTMLが出力されたら、そのサブエージェントは終了
            4. 次のPRDへ
```

- **モデルの割り当て**
  - メインエージェント(PRD作成・品質チェック・進捗管理): **Opus 5.5**(`claude-opus-5-5`)。セッションの既定モデルとして `/model` で設定済み
  - サブエージェント(モックHTML作成): **Sonnet 5.5**(`claude-sonnet-5-5`)。起動時に Agent ツールの `model: "sonnet"` で毎回指定する
  - 理由: 問題定義と解決策の質はPRD側で決まるので、考える量の多い作業をOpusに寄せる。モックはPRDに沿って実装する作業なので、速くて安いSonnetで足りる
- **サブエージェントはPRDごとに使い捨て**。PRDを書き終えるたびに新規に起動し、HTMLを書いたら完了して終わる。再利用しない
- サブエージェントに渡すもの: PRDファイルのパス、モック仕様(6章)、出力先パスのみ。会話履歴は渡さない
- サブエージェントの権限は、読み取りと指定パスへの書き込みに限る
- 順次実行が基本。75回のPRD作成+75回のサブエージェントは重いので、並列化(PRDを書き終えたものから並行してモックを作る)は5章のテンプレートが固まってから検討する
- 途中で止まっても再開できるよう、出力ファイルの有無で「済み」を判定する

## 8. ディレクトリ構成

```
aun_hayashu/prd/
├── README.md              ペルソナとペインポイント(正)
├── PLAN.md                この計画
```

## 9. 品質チェック(各PRD完成時)

- [ ] 見出しの順序が5章のとおり(版・形式の行、Risksの注記を含む)
- [ ] Goalsの各項目に効果指標が付き、Non-Goalsの各項目に理由が付いている
- [ ] 問題定義にAとBの**両方**のペインが入っている
- [ ] 同セル内の他の版と、解決策の方向性が重なっていない
- [ ] 解決策が問題定義に答えている(関係ない機能を足していない)
- [ ] モックがPRDのUser Storyを1つ以上実際に動かせる
- [ ] モックのHTMLがブラウザで開いて崩れない

## 10. 進め方の提案(いきなり75本にしない)

1. **パイロット**: 1セル(例: `A3xB4`、コミュニケーション × 専門領域のずれ。接点が自然)の3本だけ作る
2. テンプレート(5章)とモック仕様(6章)を、パイロットの出来を見て直す
3. 残り24セルを、5セルずつなど区切って実行。区切りごとにレビューする

## 11. 要確認事項

1. 2人の共通の舞台は「同じ職場」でよいか(3章)
2. 3本の差別化軸(4章)はこの3分類でよいか
3. PRDの保存先は `aun_hayashu/prd/prds/` でよいか(既存の `PRD/` 直下に置く案もある)
4. PRDは何本まとめて実行するか。75本×(PRD+モック)は時間とトークンの消費が大きい
5. 作成者名の扱い(既存PRDは「林 優太」。量産分も同じでよいか)
6. 接点が弱いセルの扱い(3章の方針でよいか)
