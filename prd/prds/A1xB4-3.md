# PRD: 設計レビューの冒頭で全分野が「変更できる期限」を宣言する制約カレンダー（A1xB4-3）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A1×B4（相手の真意がわからない × 専門領域の違いで認識がずれる）の版3。方向性は「場・仕組みを変える（チーム／組織向け）」。版1は個人が相手の分野の事情を学ぶツール、版2は2分野の間で事情を見せ合うシートを扱う。

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）は、電気・機械の両チームにまたがるプロジェクトの調整役を担当している。同じプロジェクトには、電気電子出身で入社3年目のBさん（20代後半）がいる。Bさんの部署は機械系の社員が多い。

プロジェクトの日程表には、試作や評価の節目だけが書かれている。**各分野が「いつまでなら何を変えられるか」は、日程表のどこにも書かれていない**。金型の発注、基板の改版、部品の手配の締め切りは、それぞれの担当者の頭の中にある。そのため、ある分野が変更を頼んだとき、相手の分野はすでに変えられない段階にいることがある。相手はそれを遠回しに伝え、頼んだ側は真意を読めない。

**誤解の実態**: Bさんは試作基板の発熱対策として、筐体への通気口の追加を設計レビューで提案した。機械チームのリーダーは「電気側でなんとかならないかな」と答えた。金型は前週に発注済みだったが、そのことはレビューの場で誰も口にしなかった。調整役のAさんは、両方で検討する方向と議事録に書いた。2週間後に金型の発注済みがわかり、Bさんは部品の選び直しを急ぐことになった。もしレビューの冒頭で「筐体は先週から変更不可」と共有されていれば、議論は最初から電気側の対策に向かっていた。

**気づきの実態**: 問題は個人の読み取りの力ではない。**各分野の変更期限がチームに共有されていない**ため、変更の提案が相手の締め切りの後に出され、相手は遠回しに断るしかない。誰も悪くないのに、毎回同じずれが起きる。

**練習機会の実態**: 個人が隣の分野の事情を学ぶことはできるが、具体的な案件の締め切りまでは知りようがない。設計レビューの議題は提案から始まり、各分野の現状の制約を確かめる手順はない。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げ、職場側の「ローコンテキスト化」を対策に掲げている。設計レビューでの提案が、相手の分野の締め切り後に出された件数は測られていない。

## Goals / Non-Goals

**Goals**

- 変更の提案が、相手の分野の変更期限を過ぎてから出される件数が減る（設計レビューでの変更提案のうち、相手の分野の変更期限内に出された割合を効果指標とする）
- 遠回しな断りが、期限を示した明確な返事に置き換わる（変更提案への返事のうち、制約カレンダーの期限を示して答えた割合を効果指標とする）
- 各分野の変更期限が、プロジェクトの全員に見える（「いま何が変えられないか説明できる」と答えたメンバーの割合を効果指標とする）

**Non-Goals**

- プロジェクトの日程管理ツールの置き換え（既存の日程表は残し、各分野の変更期限だけを足す）
- 変更期限を守らせる管理（期限は情報として共有し、守らせることは目的にしない）
- 全社への一斉導入（一つのプロジェクトで試す）
- 個人の学習（版1）、2者間の事情の見せ合い（版2）の範囲

## Proposed Solution / Feature Description

プロジェクトで共有する**制約カレンダー**を提供する。各分野の担当者が、「何が、いつから変更できなくなるか」（金型の発注、基板の改版、部品の手配など）を登録する。設計レビューの冒頭では、司会者がカレンダーを表示し、「今週から変更できなくなったもの」を全分野で確かめてから議題に入る。相手の分野の締め切りを、読み取らなくても見える形にする。

**主要な構成要素**:

- **変更期限の登録** — 各分野の担当者が、変更できなくなる項目とその日付、理由（発注、改版、試験開始など）を登録する。日付が変わったら担当者が更新する
- **制約カレンダー** — 全分野の変更期限を一つの時間軸に並べる。今日の位置に線を引き、すでに変更できない項目は色を変える
- **レビュー冒頭の確認** — 設計レビューの開始時に、「先週から変更できなくなった項目」と「今週中に変更できなくなる項目」を自動で一覧にする。司会者はこれを読み上げてから議題に入る
- **提案時の照合** — 変更を提案するとき、影響する項目を選ぶと、それがすでに変更期限を過ぎているかが表示される。過ぎていれば、次に変更できる時期も示す
- **期限の振り返り** — プロジェクトの節目ごとに、期限後に出された提案の件数をチームに返す。個人別には出さない

## User Stories

- **US-001 相手の分野がすでに変更できないことを知らずに提案する問題**
  利用者（Bさん）は、変更を提案する前に、相手の分野がその変更をまだ受けられるかを知りたい。それにより、遠回しな断りを相談と受け取って2週間待つ事態を避けたい。
  背景: 現状は相手の分野の変更期限が見えず、提案が締め切り後に出される。真意がわかるのは後工程が進んでからである。

- **US-002 議事録に誤った方向を書いてしまう問題**
  利用者（調整役のAさん）は、設計レビューの冒頭で、各分野が何を変えられないかを確かめたい。それにより、すでに変更できない案を「検討中」と記録する誤りを避けたい。
  背景: 現状はレビューの場で誰も変更期限を口にせず、遠回しな返事から推測するしかない。

## Open Questions

- 変更期限の登録と更新を、各分野の担当者が続けてくれるか。更新が止まると、カレンダーが誤った情報を示す
- 変更期限には「絶対に変えられない」ものと「費用をかければ変えられる」ものがある。この違いをどう表すか
- レビュー冒頭の確認に何分かけられるか
- **モックで確かめたいこと**: 制約カレンダーを見て、今日の時点で何が変えられないかがひと目でわかるか
- **モックで確かめたいこと**: 変更を提案するときの照合で、期限切れの表示が「却下」ではなく「次の機会」の案内として受け取られるか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **更新の停止** — 担当者が登録を忘れる → カレンダーが古くなる → 誤った安心を与える。軽減: 各項目に最終更新日を表示し、古い項目は印を付ける
- **期限の盾** — 期限が見える → 「期限後だから無理」と議論を打ち切る → 費用をかけてでも変えるべき判断が消える。軽減: 期限後でも「費用をかければ変更可」の区分を設ける
- **レビューの長時間化** — 冒頭の確認が長引く → レビューの時間が足りない → 確認が省かれる。軽減: 確認は「今週の変化」だけに絞り、3分以内で終わる量にする
- **特定の分野への偏り** — 期限を細かく登録する分野と、しない分野がある → 登録の少ない分野が柔軟に見える → 頼み事が集中する。軽減: 分野ごとの登録数を振り返りで共有する
