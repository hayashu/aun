# PRD: 誰の責任かを問わず「何が起き、何を学んだか」だけを共有するチームの月例・失敗共有会（A3xB5-3）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A3×B5（適切なコミュニケーション方法がわからない × 気軽に試して失敗できる場所がない）の版3。方向性は「場・仕組みを変える（チーム／組織向け）」。版1は失敗の報告の練習、版2は試す前の「やってみる宣言」を扱う。

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）と、電気電子出身で入社3年目のBさん（20代後半）は、同じ製品開発部門で働いている。部門には試作機や評価ボードがあるが、若手が自由に触れる機会は少ない。

チームでは、失敗は**個人が上司や先輩にこっそり報告するもの**になっている。誰がどんな失敗をしたかは、本人と上司しか知らない。そのため、失敗の伝え方の見本もなければ、他の人の失敗から学ぶ機会もない。若手は、失敗したら一人で上司に謝りに行くものだと思い、その場面を想像するだけで試すことをためらう。

**誤解の実態**: Aさんは評価ボードの電源を逆につないで部品を焼き、翌日まで言い出せずに注意を受けた。それ以来、試作に手を出さなくなった。Bさんはこの話を人づてに聞き、壊すことへの怖さを強めた。実は、チームのベテランの多くも、若い頃に同じような失敗をしていた。電源の逆接続は、チームで毎年のように誰かが起こしている失敗だった。しかし、その話は誰からも共有されていなかった。ベテランの失敗談を聞いていれば、AさんもBさんも「みんなやることなんだ」と思えたはずである。

**気づきの実態**: 問題は、個人の伝え方だけではない。**失敗を共有する場がチームにない**ことが原因である。失敗が個人の中に閉じていると、失敗は恥ずかしいもの、隠すものになる。チームで失敗を共有する場があり、そこでは誰の責任かを問わないと決まっていれば、失敗は学びの材料になる。失敗の伝え方の見本も、その場で自然に身につく。

**練習機会の実態**: チームには品質トラブルの報告書の仕組みがあるが、顧客に影響する大きな不具合が対象で、試作の小さな失敗は対象外である。小さな失敗ほど共有されず、同じ失敗が繰り返される。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げ、職場側の「ローコンテキスト化」を対策に掲げている。チームで同じ試作の失敗が繰り返されている件数は測られていない。

## Goals / Non-Goals

**Goals**

- 試作の小さな失敗が、チームで共有される（月あたりの共有件数を効果指標とする）
- 同じ失敗の繰り返しが減る（共有された失敗と同じ種類の失敗が、その後に起きた件数を効果指標とする）
- 若手が、失敗を恐れずに試作に手を出せる（「試作に手を出すことへの怖さ」の自己申告を効果指標とする）

**Non-Goals**

- 品質トラブル報告の置き換え（顧客に影響する不具合は既存の仕組みで扱う）
- 責任の追及（誰の失敗かを問わない。共有された失敗を評価に使わない）
- 失敗の報告の練習（版1）、試す前の宣言（版2）の範囲

## Proposed Solution / Feature Description

チームで**月に一度、30分の「失敗共有会」**を開き、その運営をWebで支える仕組みを提供する。共有する失敗は、事前に匿名か名前付きかを選んで登録する。登録の書式は「何が起きたか・なぜ起きたか・どう対応したか・次にどうするか」の4項目で、「誰の責任か」を書く欄はない。最初の数回は、ベテランが自分の若い頃の失敗を共有する。

**主要な構成要素**:

- **失敗の登録** — 何が起きたか、なぜ起きたか、どう対応したか、次にどうするかを書く。匿名か名前付きかを選べる。誰の責任かを書く欄はない
- **ベテランの失敗談** — 最初の数回は、ベテランが自分の若い頃の失敗を登録する。「みんなやること」だと若手が知るきっかけにする
- **共有会の進行** — 当日は、登録された失敗を一つ5分で共有する。進行役の画面に、失敗の一覧と残り時間を表示する。質問は「次にどうするか」に関することに限る
- **失敗の一覧** — 共有された失敗を種類ごと（電源、取り扱い、設定、測定など）に一覧で見られる。同じ種類の失敗が何度起きたかがわかる
- **防ぎ方のまとめ** — 同じ種類の失敗が複数回共有されたら、防ぎ方をチームのまとめとして残す

## User Stories

- **US-001 失敗は一人で謝りに行くものだと思って試せない問題**
  利用者（Bさん）は、他の人がどんな失敗をして、どう伝え、どう対応したかを知りたい。それにより、失敗しても一人で抱え込まずに済むと思え、試作に手を出せるようになりたい。
  背景: 現状は失敗が個人の中に閉じていて、失敗の場面を想像するだけで試すことをためらう。

- **US-002 自分だけが失敗したと思って落ち込む問題**
  利用者（Aさん）は、自分の失敗が、チームでよく起きる失敗なのかを知りたい。それにより、失敗したことで試作から遠ざかる状態を変えたい。
  背景: 現状はベテランの失敗が共有されず、自分だけがひどい失敗をしたと思い込む。

- **US-003 同じ失敗が毎年繰り返される問題**
  利用者（チームリーダー）は、チームで繰り返される失敗を知り、防ぎ方を共有したい。それにより、毎年同じ失敗で機材を壊す状態を変えたい。
  背景: 現状は小さな失敗が共有されず、同じ失敗が繰り返される。

## Open Questions

- 失敗を人前で共有することに、抵抗を感じる人はいないか。匿名の登録で十分か
- ベテランが若い頃の失敗を話してくれるか
- 責任を問わない場であることを、どう信じてもらうか。管理職が参加すると、雰囲気が変わらないか
- **モックで確かめたいこと**: 失敗の登録の書式に「誰の責任か」の欄がないことで、登録しやすいと感じられるか
- **モックで確かめたいこと**: 失敗の一覧で同じ種類の失敗の回数を見て、若手が「みんなやることなんだ」と感じられるか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **登録が集まらない** — 失敗を共有したくない → 登録がない → 会が形だけになる。軽減: 最初の数回はベテランの失敗談で会を開き、共有の雰囲気をつくる
- **責任追及の場になる** — 管理職が原因を問い詰める → 失敗した人が責められる → 誰も共有しなくなる。軽減: 質問は「次にどうするか」に限ることを進行のルールとして画面に表示する
- **匿名の推測** — 少人数のチームでは誰の失敗かわかる → 匿名の意味がない → 登録をためらう。軽減: 失敗の細部を伏せて登録できるようにし、種類と防ぎ方を中心に共有する
- **評価への転用** — 共有された失敗が記録される → 評価に使われる → 失敗を隠す。軽減: 評価に使わない方針を明記し、名前付きの登録も本人の希望でいつでも匿名に変えられるようにする
