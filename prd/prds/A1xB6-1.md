# PRD: 「もっと本質を考えて」を自分で具体例3つに置き換えて確かめる抽象ことばの具体化ノート（A1xB6-1）

版: v1（2026-11-23） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A1×B6（相手の真意がわからない × 具体と抽象を行き来する会話が苦手）の版1。方向性は「当事者の行動を支える（個人向けツール）」。版2は2人で具体例をすり合わせるカード、版3は方針に例を添えるチームのルールを扱う。A1×B4（分野の事情）は相手の分野の制約を読む話、本PRDは相手の言葉の抽象度が高すぎて中身が読めない話を扱う。

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）は、電気・機械の両チームにまたがる製品改良プロジェクトの調整役を担当している。同じプロジェクトには、電気電子出身で入社3年目のBさん（20代後半）がいる。2人の上司の課長は、方針や考え方を抽象的な言葉で語ることを好む。

2人はそれぞれ別の理由で、**抽象的な言葉の裏にある「具体的に何をしてほしいか」を読み取れない**。Aさんは、「もっと本質を考えて」が修正の指示なのか、考え方の一般論なのかを判断できない。Bさんは、抽象的な言葉を具体的な作業に落とせず、言われた内容を頭の中で「わかったつもり」のまま保留してしまう。

**誤解の実態**: Bさんは試作基板の評価結果を課長に報告した。課長は「データはわかった。でも、もっとお客さんにとっての価値から考えてみて」と返した。Bさんは「価値」が何を指すのかわからず、評価項目を増やして再報告した。課長は「そういうことじゃない」と言い、Bさんは何が違うのかを聞けなかった。Aさんも横で聞いていたが、課長が何を求めているのかを説明できなかった。後になって、課長が求めていたのは「この発熱が、使う人にとって困ることなのか」という一行の判断だったとわかった。

**気づきの実態**: 抽象的な言葉は、具体例をいくつか思い浮かべて「どれが近いか」を確かめれば、真意に近づける。しかし2人とも、抽象的な言葉を聞いた瞬間に、自分で具体例を作る手順を持っていない。そのため、わからないまま一つの解釈に賭けて外すか、聞き返せずに止まる。

**練習機会の実態**: 論理的思考の研修や本はあるが、扱うのは一般論で、「いま上司に言われたこの一言」を具体例に置き換える手助けはしない。上司に「具体的には？」と聞くのは、理解力がないと思われそうで気が引ける。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げ、職場側の「ローコンテキスト化」を対策に掲げている。抽象的な指示が具体的な作業に落ちないまま止まった件数は、社内で記録されていない。

## Goals / Non-Goals

**Goals**

- 抽象的な指示を受けたとき、自分で具体例を作ってから動ける（ノートに具体例を3つ書いた件数を効果指標とする）
- 一つの解釈に賭けて外す回数が減る（「そういうことじゃない」と言われてやり直した件数の自己申告を効果指標とする）
- 上司に確かめるときの負担が下がる（「具体的には？」ではなく「AとBのどちらに近いですか」で聞けた割合を効果指標とする）

**Non-Goals**

- 上司の言葉の正解の提示（真意は本人にしかわからず、ツールが断定すれば誤った安心を与える）
- 上司への働きかけ（版2・版3の範囲。この版は受け手が自分で準備することに限る）
- 文章の添削・敬語の修正（扱うのは具体例の作り方であり、文面ではない）
- 上司・同僚による評価や採点（他人が見る前提にすると、わからないことを書けなくなる）

## Proposed Solution / Feature Description

抽象的な言葉を受け取ったときに、**その言葉を書き写し、自分で具体例を3つ作り、どれが近いかを確かめる質問の形にする**ノートをWebで提供する。答えを出すのではなく、抽象から具体へ降りる手順を本人の中に残すことが目的である。

**主要な構成要素**:

- **ことばの書き写し** — 言われた言葉をそのまま書き、そのときの場面（報告のあと／会議中／雑談）を選ぶ
- **具体例を3つ作る** — 「もしこの言葉が○○のことなら、自分は××をする」という形で、具体例を3つ書く。3つ目が出ないときは、「作業を増やす」「判断を一行で書く」「見せ方を変える」など、具体化の方向のヒントを一つずつ出す
- **確かめる質問** — 3つの具体例から、上司に聞くための選択式の質問文（「AとBのどちらに近いですか」）を作る。本人が言い回しを直せる
- **答えの記録** — 実際に確かめた結果、どの具体例が近かったかを記録する
- **言葉の傾向** — 同じ上司のよく使う抽象的な言葉と、実際に近かった具体例を一覧にする。次に同じ言葉を聞いたとき、過去の例を見られる

## User Stories

- **US-001 抽象的な言葉を具体的な作業に落とせない問題**
  利用者（Bさん）は、「もっと価値から考えて」と言われたとき、自分で具体例をいくつか作ってから動きたい。それにより、一つの解釈に賭けて外す状態を変えたい。
  背景: 現状は言葉の意味がわからないまま作業を増やし、「そういうことじゃない」と言われる。

- **US-002 上司の言葉が指示なのか一般論なのかわからない問題**
  利用者（Aさん）は、抽象的な言葉が具体的に何を求めているのかを、選択式で上司に確かめたい。それにより、「具体的には？」と聞く気まずさを避けたい。
  背景: 現状は聞き返すと理解力がないと思われそうで、わからないまま保留してしまう。

## Open Questions

- 具体化の方向のヒントを、どこまで用意するか。多すぎると本人が考えなくなり、少なすぎると3つ目が出ない
- 上司ごとの言葉の傾向を記録することが、上司を観察しているようで抵抗感を生まないか
- 確かめる質問を上司が面倒に感じないか
- **モックで確かめたいこと**: 抽象的な言葉を一つ書いてから具体例を3つ作るまでが、報告のあとの数分で終わるか
- **モックで確かめたいこと**: 3つの具体例から作った選択式の質問を見て、本人が「これなら聞ける」と感じるか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **具体例が出ない** — 抽象的な言葉に慣れていない → 1つ目から止まる → ノートが使われない。軽減: 具体化の方向のヒントを段階的に出す
- **ノートの流出** — 上司の言葉を記録する → 他人に見られる → 上司との関係が悪くなる。軽減: 記録は端末の中だけに保存し、共有機能を持たない
- **一般化** — 「この上司はこう言う」と決めつける → 場面ごとの違いを見落とす → かえって外す。軽減: 過去の例は参考として示し、毎回3つ作る手順を省かない
