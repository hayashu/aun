# PRD: 依頼には「期限・完成度・途中確認」を必須にするチームの依頼ボード（A1xB3-3）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A1×B3（相手の真意がわからない × 自分で進める道筋を作れない）の版3。方向性は「場・仕組みを変える（チーム／組織向け）」。版1は受け手個人の期限の推測、版2は依頼の場面の復唱を扱う。

---

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）と、電気電子出身で入社3年目のBさん（20代後半）は、同じ製品開発部門で働いている。部門ではマイルストーンを決めずに仕事が渡されることが多く、進め方は担当者に任されている。

チームの依頼は、口頭やチャットの一言で行われる。期限や完成度の書き方は依頼者ごとに違い、「急ぎじゃない」「いい感じに」のように**何も決めていない依頼が多い**。依頼の一覧もないので、誰がいくつ依頼を抱え、どれがいつまでなのかは、本人の頭の中にしかない。真意を読むのが得意な人と、自分で区切りを作れる人だけが、この状態でうまく回っている。

**誤解の実態**: 同じ週に、課長はBさんに「急ぎじゃないから」とノイズ対策の案を頼み、係長は別の評価資料を「今週中に」と頼んだ。Bさんは係長の依頼を優先した。課長の依頼は実は2週間後の部長報告用で、10日後に急に必要になった。Bさんは徹夜で仕上げた。課長も係長も、Bさんが他の依頼を抱えていることを知らなかった。Aさんも「まとまったら見せて」と言われた調査を3週間抱え、方向違いで半分が使えなかった。

**気づきの実態**: 問題は個人の読み取りや段取りの力だけではない。**依頼の書き方に決まりがなく、依頼の一覧もない**ことが、ずれを生んでいる。依頼者は受け手の負荷を知らずに頼み、受け手は複数の依頼の優先度を自分で推測するしかない。

**練習機会の実態**: 部門にはプロジェクト管理ツールがあるが、大きな案件だけが登録され、日々の小さな依頼は載らない。小さな依頼ほど期限が曖昧で、ずれやすい。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げ、職場側の「ローコンテキスト化」を対策に掲げている。チーム内の依頼の期限がどれだけ曖昧なまま渡されているかは測られていない。

## Goals / Non-Goals

**Goals**

- 期限や完成度が決まっていない依頼が減る（ボードに登録された依頼のうち、期限・完成度・途中確認日がすべて入った割合を効果指標とする）
- 依頼が特定の人に重なる状態が、依頼の時点で見える（依頼者が受け手の抱えている依頼を確認してから頼んだ割合を効果指標とする）
- 締め切り直前の慌てた対応が減る（期限の3日前より後に内容や期限が変わった依頼の件数を効果指標とする）

**Non-Goals**

- 大きな案件のプロジェクト管理（既存のツールの領域。本書は数日〜数週間の小さな依頼に限る）
- 個人の作業量の評価（依頼の件数を評価に使うと、依頼を受けなくなる）
- 依頼の自動割り振り（誰に頼むかは依頼者が決める）
- 受け手個人の期限の推測（版1）、依頼の場面の復唱（版2）の範囲

## Proposed Solution / Feature Description

チームで共有する**依頼ボード**を提供する。依頼を出すときは、期限・完成度（たたき台／一次案／ほぼ完成）・途中確認日の3項目を必須にする。「急ぎじゃない」は選べず、代わりに期限の幅（今週／2週間以内／1か月以内）を選ぶ。依頼を出す前に、受け手が抱えている依頼の一覧が表示される。真意を読む必要と、受け手が一人で区切りを作る負担を、依頼の書式でなくす。

**主要な構成要素**:

- **依頼の書式** — 依頼の内容、期限の幅、完成度、途中確認日、使い道（任意）を入力する。期限の幅と完成度と途中確認日は必須にする
- **受け手の負荷の表示** — 依頼を出す前に、受け手が抱えている依頼と、その期限が並んで見える。重なる期限があれば警告する
- **受け手の受諾** — 受け手は「受ける／期限を相談したい」を選ぶ。相談したい場合は、希望の期限を一つ返す
- **途中確認の通知** — 途中確認日に、依頼者と受け手の両方へ知らせる
- **チームの振り返り** — 一か月ごとに、必須項目の記入率、期限の変更件数、依頼の偏りをチームに返す。個人別の件数は出さない
- **依頼の型の共有** — よく出る依頼（評価資料、調査まとめなど）の書式を、チームの型として登録できる。第2段階に置き、現時点のプロトタイプには入っていない

## User Stories

- **US-001 曖昧な期限の依頼が重なる問題**
  利用者（Bさん）は、複数の依頼の期限と完成度を、依頼の時点で知りたい。それにより、「急ぎじゃない」依頼が実は急ぎだったと10日後に知る事態を避けたい。
  背景: 現状は依頼ごとに書き方が違い、優先度を本人が推測するしかない。推測を外すと、本当の期限の直前に知らされ、準備の時間がない。

- **US-002 受け手の負荷を知らずに頼む問題**
  利用者（課長）は、依頼を出す前に、受け手がすでに何を抱えているかを知りたい。それにより、無理な重なりを避け、必要なら期限を調整したい。
  背景: 現状は受け手の依頼が見えず、他の人の依頼と重なっていることを知らないまま頼む。

- **US-003 途中で見せる時点がわからない問題**
  利用者（Aさん）は、依頼の時点で途中確認の日を決めておきたい。それにより、完成してから方向違いがわかる事態を避けたい。
  背景: 現状は「まとまったら見せて」と言われ、途中で見せてよいのかがわからない。

## Open Questions

- 必須項目を増やすと、依頼者が口頭の依頼に戻らないか。必須項目は3つが限度か
- 受け手の負荷の表示は、受け手にとって「忙しさが丸見え」で嫌ではないか
- 部門の他のチームから来る依頼も載せるか。載せなければ負荷の表示が不完全になる
- **モックで確かめたいこと**: 依頼者が依頼を出す前に受け手の負荷を見て、期限を自然に調整したくなるか
- **モックで確かめたいこと**: 「急ぎじゃない」を選べない書式が、依頼者にとって窮屈すぎないか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **口頭への逆戻り** — 書式が面倒 → 依頼者が口頭で頼む → ボードが空になる。軽減: 書式を1画面に収め、よく使う依頼は前回の内容を複製できるようにする
- **監視の道具化** — 依頼の一覧が見える → 上司が部下の忙しさを評価に使う → 受け手が受諾を嫌がる。軽減: 個人別の件数を集計せず、評価に使わない方針を明記する
- **受諾の圧力** — 「期限を相談したい」を押しにくい → 無理な依頼を受ける → 結局ぎりぎりになる。軽減: 相談を選んだ件数を、受け手の評価ではなく依頼の重なりの指標として振り返りに出す
- **特定の人のための仕組みと見られる** — 外国籍社員や若手への配慮に見える → 周囲が使わない → 本人が浮く。回避: チーム全員の依頼の書式として導入する
