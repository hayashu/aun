# PRD: チームの過去の仕事の「実際にかかった日数」を区切りごとに引ける実績日数ライブラリ（A4xB3-3）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A4×B3（失敗の原因がわからない × 自分で進める道筋を作れない）の版3。方向性は「場・仕組みを変える（チーム／組織向け）」。版1は本人の見積もり癖ノート、版2は上司との遅れの経緯たどりを扱う。

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）と、電気電子出身で入社3年目のBさん（20代後半）は、同じ製品開発部門で働いている。部門ではマイルストーンを決めずに仕事が渡されることが多く、進め方は担当者に任されている。

チームの仕事の見積もりは、**それぞれの担当者の勘**で行われている。ベテランは経験から「この評価なら2週間」とわかるが、新しく来た人や、自分で区切りを作るのが苦手な人には、その感覚がない。見積もりを外して遅れても、どれくらいが普通だったのかを知る手段がないので、自分の見積もりが甘かったのか、仕事が特別に大変だったのかもわからない。チームには過去の仕事の記録があるが、実際に何日かかったかは残っていない。

**誤解の実態**: Bさんは評価資料を「1週間」と見積もり、2週間かかった。上司に「見積もりが甘い」と言われたが、Bさんはどれくらいが普通なのかを知らなかった。実は、チームの他の人が同じ種類の評価資料を作ったときも、だいたい2週間かかっていた。Bさんの見積もりが甘かったのは確かだが、それはBさんだけの問題ではなく、普通の日数を知る手段がなかったことが原因だった。Aさんも、調査の仕事を「3日」と見積もったが、チームの過去の調査は平均で8日かかっていた。

**気づきの実態**: 問題は個人の見積もりの力だけではない。**チームの仕事に実際にかかった日数が共有されていない**ことが原因である。過去の同じ種類の仕事が何日かかったかがわかれば、新しく来た人もそれを参考に見積もれる。遅れたときも、普通の日数と比べて、自分の見積もりが甘かったのか、仕事が特別だったのかを判断できる。

**練習機会の実態**: チームの進捗管理は、締め切りに間に合ったかどうかだけを記録し、実際の日数は残さない。見積もりの方法を教わる機会もない。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げ、職場側の「ローコンテキスト化」を対策に掲げている。チームの仕事の見積もりと実績のずれは測られていない。

## Goals / Non-Goals

**Goals**

- チームの仕事の実績日数が、種類と区切りごとに共有される（終わった仕事のうち、実績日数が登録された割合を効果指標とする）
- 新しく来た人の見積もりの精度が上がる（ライブラリを参照して見積もった仕事の、見積もりに対する実績の比を効果指標とする）
- 遅れたときに、原因を普通の日数と比べて判断できる（遅れた仕事のうち、ライブラリの日数と比べて原因を説明できた割合の自己申告を効果指標とする）

**Non-Goals**

- 個人の作業速度の評価（実績日数は仕事の種類ごとに集計し、個人別の速さを比べない）
- プロジェクト管理ツールの置き換え（ライブラリは見積もりの参考情報だけを扱う）
- 本人の見積もり癖（版1）、上司との経緯たどり（版2）の範囲

## Proposed Solution / Feature Description

チームの仕事が終わるたびに、**仕事の種類（評価資料、調査、試作、図面修正など）と、区切りごとの実績日数を登録し、誰でも引けるライブラリにする**仕組みを提供する。新しい仕事を受けたら、同じ種類の過去の仕事の実績日数（中央値と幅）を区切りごとに見て、見積もりの参考にする。

**主要な構成要素**:

- **実績の登録** — 仕事が終わったら、仕事の種類と、区切り（調べる、作る・測る、まとめる、確認を待つ）ごとの実績日数を登録する。担当者の名前は登録しない
- **種類ごとの実績** — 仕事の種類を選ぶと、過去の実績日数の中央値と幅（短い場合と長い場合）を区切りごとに示す
- **見積もりの参考** — 新しい仕事の見積もりを書くとき、同じ種類の実績を横に表示する。本人の見積もりが実績の幅から大きく外れていたら知らせる
- **よくある遅れ** — 同じ種類の仕事で、どの区切りが遅れやすいかを示す（「評価資料はまとめる作業が長くなりやすい」）
- **ライブラリの充実度** — 種類ごとの登録件数を表示する。件数が少ない種類は、参考の精度が低いことを示す

## User Stories

- **US-001 普通の日数を知らずに見積もる問題**
  利用者（Bさん）は、仕事を見積もるときに、チームの過去の同じ種類の仕事が何日かかったかを知りたい。それにより、勘だけで見積もって大きく外す事態を避けたい。
  背景: 現状は実績日数が共有されず、新しく来た人には見積もりの手がかりがない。

- **US-002 遅れの原因が自分の見積もりか仕事の大変さかわからない問題**
  利用者（Aさん）は、遅れたときに、普通の日数と比べて原因を判断したい。それにより、すべてを自分の計画性のせいにする状態を変えたい。
  背景: 現状は普通の日数がわからず、遅れの原因を判断できない。

- **US-003 チームの見積もりが勘に頼っている問題**
  利用者（チームリーダー）は、チームの仕事の見積もりを、実績に基づいて行えるようにしたい。それにより、締め切りの設定を現実的にしたい。
  背景: 現状は見積もりが担当者の勘に頼り、遅れが起きやすい。

## Open Questions

- チームのメンバーが実績日数を登録し続けてくれるか
- 仕事の種類の分け方が、実際の仕事の多様さに合うか。同じ「評価資料」でも、規模が大きく違うことがある
- 担当者の名前を登録しなくても、少人数のチームでは誰の仕事か推測できてしまうのではないか
- **モックで確かめたいこと**: 見積もりを書くときに実績の中央値と幅が横に出て、本人が見積もりを自然に見直したくなるか
- **モックで確かめたいこと**: 「よくある遅れ」を見て、遅れやすい区切りを見積もりに反映できるか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **登録が続かない** — 仕事が終わるたびに登録する → 忘れる → ライブラリが育たない。軽減: 仕事の完了報告の手順に登録を組み込み、区切りごとに日数を選ぶだけにする
- **実績への過度な依存** — 中央値をそのまま使う → 仕事ごとの違いを考えない → かえって外す。軽減: 中央値と幅を必ず並べて示し、幅の理由を考えるよう促す
- **個人の速さの比較** — 実績が見える → 遅い人が特定される → 正直に登録しなくなる。軽減: 担当者の名前を残さず、個人別の集計をしない
- **締め切りの硬直化** — 実績の中央値が締め切りの基準になる → 余裕がなくなる → 遅れが増える。軽減: 締め切りは幅の長い側を参考に決めることを推奨する
