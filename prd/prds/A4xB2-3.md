# PRD: 部署の設計ミスを「原因と防ぎ方」付きで集め、設計前に引ける設計ミス事例集（A4xB2-3）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A4×B2（失敗の原因がわからない × ハードウェアの知識が足りず焦る）の版3。方向性は「場・仕組みを変える（チーム／組織向け）」。版1は本人の原因切り分け、版2は先輩との15分の振り返りを扱う。A3×B5-3（試作の失敗共有会）とは異なり、本PRDは設計レビューで見つかる設計上のミスを、設計前に参照できる事例として残すことを扱う。

---

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）と、電気電子出身で入社3年目のBさん（20代後半）は、同じ製品開発部門で働いている。部門は機械系の社員が多く、筐体・機構・材料の知識が前提として会話が進む。

部門の設計レビューでは、毎回いくつもの設計ミスが見つかる。基板とリブの干渉、熱のこもりやすい部品配置、コネクタの挿し間違いを防ぐ形状の不足。しかし、**見つかったミスとその原因は、レビューの議事録に「修正済み」と残るだけ**で、次の設計者が参照できる形になっていない。ベテランは経験からこれらのミスを避けられるが、新しく来た人は同じミスを一から経験するしかない。原因がわからないまま、知識不足だと焦る。

**誤解の実態**: Bさんは、基板の取り付け穴が筐体のリブと干渉するミスをした。原因は、機械側の最新の筐体データを確かめずに配置したことだった。実は、同じミスは2年前にも別の若手が起こしていた。議事録には「干渉あり、修正済み」とだけ書かれていた。原因と防ぎ方が残っていれば、Bさんは設計の前にそれを見て、同じミスを避けられた。Aさんも、評価条件の書き漏れという、過去に何度も起きていたミスを繰り返した。

**気づきの実態**: 問題は個人の知識や振り返りだけではない。**部署の設計ミスの経験が、原因と防ぎ方の形で蓄積されていない**ことが原因である。蓄積されていれば、新しく来た人は設計の前に、自分がこれからする設計でよく起きるミスを知れる。そして、ミスの原因が知識だけでなく、手順や確認にもあることを、事例から学べる。

**練習機会の実態**: 部門には設計基準書があるが、「こうすべき」という規則が書かれているだけで、なぜその規則があるのか、守らないとどんなミスが起きるのかは書かれていない。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げ、職場側の「ローコンテキスト化」を対策に掲げている。部門で同じ設計ミスが繰り返されている件数は測られていない。

## Goals / Non-Goals

**Goals**

- 設計レビューで見つかったミスが、原因と防ぎ方付きで残る（レビューで指摘されたミスのうち、事例集に登録された割合を効果指標とする）
- 同じ設計ミスの繰り返しが減る（事例集にあるミスと同じ種類のミスが、レビューで指摘された件数を効果指標とする）
- 設計者が、設計の前に事例を参照する（設計の着手時に、事例集を参照した割合を効果指標とする）

**Non-Goals**

- 設計基準書の置き換え（基準書は残し、事例集は基準の理由と具体例を補う）
- ミスをした人の記録（誰がミスをしたかは残さない）
- 品質トラブルのデータベースの置き換え（顧客に影響する不具合は既存の仕組みで扱う）
- 本人の原因切り分け（版1）、先輩との振り返り（版2）の範囲

## Proposed Solution / Feature Description

設計レビューで見つかったミスを、**「何が起きたか・原因（知識／手順／確認／伝達）・防ぎ方」の形で登録し、設計の種類ごとに引ける事例集**を提供する。登録はレビューの議事録を書く人が行い、ミスをした人の名前は残さない。設計を始めるときに、設計の種類を選ぶと、その種類でよく起きるミスが一覧で出る。

**主要な構成要素**:

- **事例の登録** — レビューで指摘されたミスを、何が起きたか、原因の分類、防ぎ方の3つで登録する。図や写真を一枚添付できる。ミスをした人の名前は登録しない
- **設計の種類ごとの一覧** — 基板配置、筐体設計、熱設計、評価条件などの種類ごとに、事例を一覧にする。同じ事例が何度起きたかを表示する
- **設計前の確認** — 設計を始めるときに種類を選ぶと、その種類でよく起きるミスの上位5件が表示される。設計者は確認したものに印を付ける
- **原因の分布** — 事例を原因ごとに集計し、部署でどの原因のミスが多いかを示す。知識以外の原因（手順、確認、伝達）が多いことが見えれば、知識不足だけに焦る必要がないとわかる
- **基準書とのつなぎ** — 事例から、関係する設計基準書の項目へつなげる。基準の理由が具体例でわかる

## User Stories

- **US-001 過去に何度も起きたミスを一から経験する問題**
  利用者（Bさん）は、設計を始める前に、その種類の設計でよく起きるミスを知りたい。それにより、2年前に別の若手が起こした干渉を、同じように繰り返す事態を避けたい。
  背景: 現状はミスが議事録に「修正済み」と残るだけで、原因と防ぎ方が参照できない。新しく来た人は同じミスを一から経験する。

- **US-002 ミスの原因が知識不足だけだと思い込む問題**
  利用者（Aさん）は、部署で起きるミスの原因に、知識以外のものが多いことを知りたい。それにより、ミスのたびに知識不足だと焦る状態を変えたい。
  背景: 現状はミスの原因が共有されず、自分の知識不足だと思い込む。

- **US-003 ベテランの経験が引き継がれない問題**
  利用者（部門のベテラン）は、自分が経験から避けているミスを、新しく来た人に伝えたい。それにより、毎年同じミスの指摘をしなくて済むようにしたい。
  背景: 現状はミスの経験が個人の頭の中にしかなく、レビューのたびに同じ指摘を繰り返している。

## Open Questions

- 議事録を書く人が、事例の登録に時間を使ってくれるか
- 原因の分類を、議事録を書く人が正しく判断できるか。ミスをした本人に確かめる必要があるか
- ミスをした人の名前を残さなくても、少人数の部署では推測できてしまうのではないか
- **モックで確かめたいこと**: 設計前の確認で、上位5件のミスを見て「これは自分もやりそう」と感じられるか
- **モックで確かめたいこと**: 原因の分布を見て、知識以外の原因が多いことが一目でわかり、焦りが和らぐか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **登録の停滞** — 議事録係が忙しい → 事例が登録されない → 事例集が育たない。軽減: 登録の項目を3つに絞り、議事録の書式に組み込む
- **ミスをした人の特定** — 少人数で推測できる → 本人が恥ずかしく感じる → ミスを隠す。軽減: 事例の細部を一般化して登録し、時期も月単位にする
- **形骸化** — 設計前の確認が形式的になる → 印を付けるだけ → ミスが減らない。軽減: 上位5件に絞り、設計の種類に合ったものだけを出す
- **評価への転用** — 事例数が部署の評価に使われる → 登録を控える → 事例集が育たない。軽減: 事例数を評価に使わない方針を明記する
