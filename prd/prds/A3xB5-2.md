# PRD: 試す前に「何を試し、壊れたらどうするか」を宣言して先輩の了承を得る「やってみる宣言」（A3xB5-2）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A3×B5（適切なコミュニケーション方法がわからない × 気軽に試して失敗できる場所がない）の版2。方向性は「2人の間をつなぐ（コミュニケーション設計）」。版1は失敗の報告の練習、版3はチームの責めない失敗共有会を扱う。

---

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）と、電気電子出身で入社3年目のBさん（20代後半）は、同じ製品開発部門で働いている。部門には試作機や評価ボードがあるが、若手が自由に触れる機会は少ない。

若手が何かを試したいとき、**試してよいかをどう頼めばよいか、失敗したらどう伝えればよいか**がわからない。頼み方がわからないので、試すことを先輩や上司に言い出せない。言い出さずに試して失敗すると、「なぜ相談しなかったのか」と言われる。言い出して試して失敗しても、どこまでの失敗が許されていたのかが曖昧なので、責められるのではないかと不安になる。

**誤解の実態**: Bさんは、評価ボードの部品を付け替えて、ノイズが減るかを試したいと考えた。先輩に頼もうとしたが、どう切り出せばよいかわからず、結局頼まなかった。Aさんは別の試作で、先輩に何も言わずに設定を変えて試し、ボードを不安定にしてしまった。先輩は「試すのはいいけど、先に一言言って」と言った。Aさんは、先に言えば止められると思っていた。先輩は、先に言われれば「壊れても大丈夫な範囲」を教えるつもりだった。

**気づきの実態**: 先輩が求めていたのは、試すことを止めることではなく、**試す前に共有すること**だった。何を試し、どこまで壊れる可能性があり、壊れたらどうするかを先に話していれば、先輩は安心して任せられ、若手は安心して試せる。失敗しても、それは事前に了承された範囲の出来事になる。しかし、その共有の形がないので、若手は言い出せず、先輩は知らないうちに試される。

**練習機会の実態**: 試作の承認には正式な手続きがあるが、大きな試作を対象としており、小さな試しには重すぎる。小さな試しは口頭で済まされるか、何も言わずに行われる。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、対策として「コミュニケーションのローコンテキスト化」を掲げている。若手が小さな試しを言い出せずにあきらめている件数は、部門では測られていない。

## Goals / Non-Goals

**Goals**

- 若手が小さな試しを言い出せる（月あたりのやってみる宣言の件数を効果指標とする）
- 試す前に、壊れたときの対応が合意されている（宣言のうち、「壊れたら」の欄が埋まり先輩が了承した割合を効果指標とする）
- 失敗しても、責められる不安が小さい（宣言して試して失敗した若手のうち、「安心して報告できた」と答えた割合を効果指標とする）

**Non-Goals**

- 正式な試作承認の置き換え（大きな試作は既存の手続きで行う）
- 試した結果の評価（成功か失敗かを評価に使わない）
- 失敗の報告の練習（版1）、チームの失敗共有会（版3）の範囲

## Proposed Solution / Feature Description

若手が小さな試しをする前に、**「何を試すか・使う機材・壊れるかもしれないこと・壊れたらどうするか」を1枚の宣言に書いて先輩に送り、先輩が了承する**Webの仕組みを提供する。宣言には、試したあとの結果（うまくいった／うまくいかなかった／壊れた）を書く欄がある。壊れたことも、宣言の中の想定された結果として、気まずさなく報告できる。

**主要な構成要素**:

- **やってみる宣言** — 何を試すか、使う機材、壊れるかもしれないこと、壊れたらどうするか（誰に連絡するか、代わりの機材はあるか）を書く。選択式と一行で、2分以内に書ける量にする
- **先輩の了承** — 先輩は、「どうぞ」「この範囲までならどうぞ（条件）」「今回は待って（理由）」から選ぶ。条件には「この部品は替えがないので触らないで」のような一言を書ける
- **結果の報告** — 試したあと、「うまくいった／うまくいかなかった／壊れた」を選び、一行で書く。「壊れた」も選択肢の一つとして並べることで、報告の気まずさを下げる
- **宣言の一覧** — 若手と先輩が、過去の宣言と結果を見られる。先輩は、若手がどんなことを試しているかを知れる
- **壊れたときの連絡** — 「壊れた」を選ぶと、宣言で決めた連絡先に知らせが届く

## User Stories

- **US-001 試してよいかを頼めない問題**
  利用者（Bさん）は、小さな試しをするときに、気軽に先輩の了承を得る形がほしい。それにより、頼み方がわからずに試すことをあきらめる状態を変えたい。
  背景: 現状は小さな試しの頼み方がなく、言い出せずにあきらめる。

- **US-002 試したあとに「先に言って」と言われる問題**
  利用者（Aさん）は、試す前に、壊れたときの対応を先輩と決めておきたい。それにより、失敗したときに責められる不安なく報告したい。
  背景: 現状は先に言うと止められると思って黙って試し、失敗してから注意を受ける。

- **US-003 知らないうちに機材を試される問題**
  利用者（先輩）は、若手が何を試すかを先に知り、壊れても大丈夫な範囲を伝えたい。それにより、安心して若手に任せたい。
  背景: 現状は若手が黙って試し、壊れてから知る。

## Open Questions

- 先輩が宣言に毎回応じてくれるか。宣言が多いと先輩の負担になる
- 「今回は待って」が多いと、若手が宣言をやめないか
- 宣言の対象をどこまでにするか。設定を少し変えるだけでも宣言が必要か
- **モックで確かめたいこと**: 若手がやってみる宣言を2分以内に書け、先輩が1分以内で了承できるか
- **モックで確かめたいこと**: 結果の報告で「壊れた」を選ぶことが、気まずさなくできるか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **手続きの重さ** — 小さな試しにも宣言が必要 → 面倒になる → 黙って試すことに戻る。軽減: 宣言は2分で書ける量にし、機材を壊す可能性がない試しは対象外にする
- **先輩の保守化** — 了承すると責任を感じる → 「待って」ばかり選ぶ → 試す機会が減る。軽減: 了承は「把握した」の意味であり、結果の責任は問わないことを明記する
- **監視の道具化** — 宣言の一覧が見える → 若手の試しを管理する道具になる → 若手が嫌がる。軽減: 一覧は若手と先輩の2人だけが見られる設定にする
- **評価への転用** — 結果が記録される → 失敗の数が評価に使われる → 宣言しなくなる。軽減: 結果を評価に使わない方針を明記する
