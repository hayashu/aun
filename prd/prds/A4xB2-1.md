# PRD: 設計ミスの原因を「知識・手順・確認・伝達」に切り分け、学ぶべき範囲を絞る原因切り分けノート（A4xB2-1）

版: v1（2026-11-22） / 形式: Alpha+ PRD 101（Slide 27 テンプレート順）
※ セル A4×B2（失敗の原因がわからない × ハードウェアの知識が足りず焦る）の版1。方向性は「当事者の行動を支える（個人向けツール）」。版2は先輩との15分の振り返り、版3は部署の設計ミス事例集を扱う。

## Overview / Problem Statement

日本の製造業A社で、外国籍社員のAさん（30代、日本での滞在10年、JLPT N1保持）と、電気電子出身で入社3年目のBさん（20代後半）は、同じ製品開発部門で働いている。部門は機械系の社員が多く、筐体・機構・材料の知識が前提として会話が進む。

2人は、設計レビューでミスを指摘されることがある。ミスそのものは誰にでもあることだが、問題は**ミスの原因が何なのかがわからない**ことにある。知識が足りなかったのか、手順を飛ばしたのか、確認が甘かったのか、伝え方がまずかったのか。原因がわからないので、すべてを「自分の知識不足」と受け取り、焦ってやみくもに勉強を始める。しかし、原因が知識でなかった場合、勉強しても同じミスを繰り返す。

**誤解の実態**: Bさんは、基板の取り付け穴の位置が筐体のリブと干渉していることを設計レビューで指摘された。Bさんは「機械の知識が足りないからだ」と考え、週末に筐体設計の教科書を読み始めた。しかし、実際の原因は知識ではなかった。機械側から最新の筐体データを受け取らず、古いデータで配置していたという手順の問題だった。翌月、Bさんは別の基板でまた同じ干渉を起こした。Aさんも、評価の条件の書き漏れを指摘されて材料力学を勉強し直したが、原因は確認のチェックリストを使っていなかったことだった。

**気づきの実態**: ミスの原因は、大きく分けて知識、手順、確認、伝達のどれかであることが多い。原因を切り分ければ、対策も絞れる。知識なら学ぶ、手順なら手順を確かめる、確認ならチェックの方法を変える、伝達なら受け渡しの形を変える。2人は切り分けの方法を知らず、焦りから「知識不足」に決めつけてしまう。

**練習機会の実態**: 設計レビューでは、ミスの指摘はされるが、原因の分析はされない。品質部門の不具合分析の手法はあるが、大きな不具合を対象としており、個人の小さな設計ミスには使われない。

**背景**: 経済産業省「高度外国人材研究会 報告書」（2024年7月26日）は、外国人材の職場への不満として「暗黙の了解が理解できない」を挙げている。若手の設計ミスの再発率は、部門では測られていない。

## Goals / Non-Goals

**Goals**

- 同じ設計ミスの繰り返しが減る（記録したミスと同じ種類のミスが、その後に起きた件数を効果指標とする）
- ミスの原因が、知識以外にもあると気づける（記録したミスのうち、原因を知識以外に切り分けた割合を効果指標とする）
- 知識不足への焦りが、具体的な学習範囲に変わる（「何を学べばよいかわかっている」の自己申告を効果指標とする）

**Non-Goals**

- 設計の技術的な正解の提示（ツールは原因を切り分けるだけで、技術の答えは出さない）
- 品質部門の不具合分析の置き換え（大きな不具合は既存の手法で扱う）
- 先輩との振り返り（版2）、部署の事例集（版3）の範囲

## Proposed Solution / Feature Description

設計レビューで指摘されたミスを記録すると、**原因を「知識」「手順」「確認」「伝達」の4つに切り分ける質問に順に答えさせ、原因ごとの対策を本人に選ばせる**個人向けWebツールを提供する。原因が知識だった場合だけ、学ぶ範囲を絞って示す。焦りからの決めつけを、切り分けで止める。

**主要な構成要素**:

- **ミスの記録** — 指摘されたミスと、指摘された場面を書く
- **切り分けの質問** — 「必要な情報（最新の図面など）は手元にあったか」「手順のどこかを飛ばしたか」「確認の方法を決めていたか」「受け渡しで情報が欠けたか」「そもそも知らなかったか」の順に答えさせる。最初に知識を聞かないことで、決めつけを防ぐ
- **原因ごとの対策** — 切り分けた原因に応じて、対策の候補を示す（手順なら「最新データの確認を手順に入れる」、確認なら「チェックリストを作る」、伝達なら「受け渡しの形を相手と決める」）
- **学ぶ範囲** — 原因が知識だった場合だけ、そのミスに関わる範囲を一つに絞って示す（「筐体設計全般」ではなく「リブの配置と基板の取り付け穴の関係」）
- **ミスの傾向** — 記録したミスを原因ごとに集計し、本人の傾向（手順の飛ばしが多い、など）を示す

## User Stories

- **US-001 ミスをすべて知識不足と決めつける問題**
  利用者（Bさん）は、設計ミスの原因が知識なのか、手順や確認なのかを切り分けたい。それにより、教科書を読んでも同じミスを繰り返す事態を避けたい。
  背景: 現状は焦りからすべてを知識不足と受け取り、やみくもに勉強する。原因が手順だった場合、同じミスが翌月に繰り返される。

- **US-002 何を学べばよいかわからず焦る問題**
  利用者（Aさん）は、ミスの原因が知識だった場合に、学ぶ範囲を絞りたい。それにより、教科書を最初から読み直すような遠回りを避けたい。
  背景: 現状はミスのたびに広い範囲を勉強し直し、業務に必要な範囲にたどり着かない。

## Open Questions

- 本人が自分のミスの原因を正直に切り分けられるか。手順を飛ばしたことを認めたくない気持ちが働かないか
- 4つの分類で足りるか
- **モックで確かめたいこと**: 切り分けの質問に答えるうちに、「知識不足ではなかった」と気づける流れになっているか
- **モックで確かめたいこと**: ミスの傾向を見て、焦りではなく「ここを変えればよい」と感じられるか

## Risks（教材外補強 — PRD 101 に Risks の形式は無い）

- **自己批判の強化** — ミスを細かく分析する → 自分を責める → 焦りが増す。軽減: 原因は「仕組みで防げること」として示し、対策を中心に置く
- **切り分けの誤り** — 本人が原因を間違える → 違う対策をする → 同じミスが続く。軽減: 版2の先輩との振り返りと組み合わせ、切り分けを確かめる機会をつくる
- **記録の負担** — ミスのたびに記録する → 面倒になる → 使われなくなる。軽減: 質問は選択式にし、3分で終わる量に絞る
- **他人の責任にする** — 「伝達」に切り分けやすい → 相手のせいにする → 関係が悪くなる。軽減: 伝達の対策は「受け渡しの形を相手と決める」とし、相手を責める形にしない
